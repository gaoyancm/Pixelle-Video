## 2. 阶段目标

阶段02-D建立本地、可靠、可替换的素材与输出资产内核，使平台形成以下最小闭环：

```text
上传字节
→ 注册输入资产
→ 以资产UUID创建持久化任务
→ Worker受控读取输入
→ Provider执行
→ 输出写入受管Store
→ 输出资产登记
→ 任务与输入/输出建立关系
→ 按资产UUID查询及受控下载
→ 软删除、引用保护与安全清理
```

本阶段必须使数据库资产记录成为素材和输出的事实源。真实文件路径、绝对路径及Provider路径不得成为公开资产身份。

## 6. 数据模型

### 6.1 `media_assets`

至少包含以下语义字段；具体SQLAlchemy类型应沿用仓库现有风格并兼容SQLite：

| 字段 | 约束与语义 |
|---|---|
| `id` | UUID字符串主键，由服务端生成，不可变。 |
| `kind` | 严格枚举：`input`或`output`。 |
| `state` | 至少表达`available`、`disabled`、`deleted`、`missing`；非法跃迁必须拒绝。 |
| `backend` | 当前仅允许`local`，不得把Windows盘符或绝对路径写入。 |
| `object_key` | Store内部不透明对象键；唯一、相对、无`.`/`..`、无绝对路径语义。 |
| `original_filename` | 仅作展示元数据；不得参与磁盘路径解析。 |
| `media_type` | 受控媒体类别；不得仅信任客户端声明。 |
| `mime_type` | 服务端校验/推断后的值。 |
| `size_bytes` | 非负整数，与实际字节一致。 |
| `sha256` | 小写64位十六进制摘要，与实际字节一致。 |
| `source` | 至少区分`upload`、`generated`及内部可信导入（如实现）。 |
| `created_at`、`updated_at` | UTC时间，遵循现有时间工具。 |
| `disabled_at`、`deleted_at` | 可空；必须与状态一致。 |

可加入实现所必需且有测试覆盖的字段，但不得加入用户、租户、项目、计费或云厂商专属字段。

### 6.2 `media_job_assets`

至少包含：

| 字段 | 约束与语义 |
|---|---|
| `job_id` | 指向`media_jobs.id`的外键。 |
| `asset_id` | 指向`media_assets.id`的外键。 |
| `direction` | `input`或`output`。 |
| `role` | 受控角色，如`input_image`、`generated_video`。 |
| `position` | 非负顺序号，用于稳定表达多输入/多输出。 |
| `created_at` | UTC创建时间。 |

必须建立必要的唯一约束和索引，至少防止同一任务、方向、位置重复，并支持按任务查资产、按资产查引用。

### 6.3 关系规则

- 新任务输入关系必须在任务创建事务中建立；
- 只有`available + input`资产可用于新任务；
- 输出只能由受信任内部执行路径创建，公开上传不得伪装为输出；
- 输出资产登记成功后才允许成为公开可下载资产；
- 重试复制父任务输入关联，禁止复制父任务输出关联；
- 资产软删除不得破坏历史关系；
- 有任何任务关系时，普通物理删除必须拒绝；
- 不得依靠JSON字符串模拟外键完整性。

## 8. 本地Store契约

### 8.1 接口

Store接口至少支持：

- 以流式方式写入临时对象；
- 完成校验后原子发布；
- 打开受控读取流；
- 查询存在性及必要元数据；
- 删除临时对象；
- 经受控Service删除正式对象；
- 对账时枚举02-D受管对象键或提供等价能力。

核心领域和API不得直接依赖`Path.cwd()`、Windows盘符或绝对路径。

### 8.2 路径安全

- object key由服务端生成，客户端文件名不得成为最终路径；
- 拒绝绝对路径、drive、UNC、反斜杠、`.`、`..`、空段和NUL；
- 解析后必须校验最终路径仍位于配置根；
- 必须防止符号链接、junction或等价重解析点逃逸；
- 读取和删除必须重新验证边界，不得只在上传时验证一次；
- 不得跟随受管根外目标；
- 错误响应和日志不得泄露绝对路径。

### 8.3 写入一致性

上传和输出必须遵循：

1. 写入唯一临时对象；
2. 流式计算size和SHA256，并实施大小上限；
3. 完成媒体类型/内容最低限度校验；
4. 原子发布到最终object key；
5. 创建数据库资产记录及关系；
6. 任一步失败时执行明确补偿；
7. 崩溃窗口产生的孤儿必须可被对账识别。

不得使用多个执行者可能共享的固定`.tmp`文件名。

## 9. 上传与输入注册

### 9.1 公开上传

实现一个上传即注册端点。建议为：

`POST /api/assets`

请求必须：

- 使用受控文件上传；
- 接受独立的幂等键；
- 不接受客户端指定`asset_id`、`backend`、`object_key`或服务器路径；
- 不接受外部URL；
- 不允许创建`kind=output`；
- 使用配置的上传上限，默认值应与现有`max_upload_size`一致或经证据说明；
- 不能一次性无上限读入内存；
- 校验空文件、超限文件、危险文件名、扩展名/MIME不一致和不支持媒体类型。

幂等语义必须明确：

- 同一幂等键与相同规范请求/相同内容重复提交，返回同一资产；
- 同一幂等键与不同内容冲突，返回稳定冲突响应；
- 并发相同请求不能生成两个有效资产或两个永久文件；
- 幂等键不得替代资产UUID。

### 9.2 任务创建校验

保留02-C公开字段名`asset_id`，但从02-D开始：

- 新请求中的值必须是合法资产UUID；
- Service必须查询数据库资产；
- 必须要求`kind=input`且`state=available`；
- 必须验证其media type适用于目标工作流和角色；
- 数据库记录与文件缺失时不得排队，返回稳定、脱敏错误；
- 创建任务和输入关系应在同一数据库事务中完成；
- 响应不得公开object key、受管根或绝对路径。

### 9.3 legacy兼容

- 冻结HEAD之前已经存在的任务可继续由Worker读取原路径型引用；
- legacy判断必须基于历史记录/明确格式和受控代码路径，不得把任意新无效UUID当作路径回退；
- 新API请求不得触发legacy回退；
- 新建任务、重试任务及新输出不得产生路径型资产ID；
- legacy解析继续受`managed_asset_root`边界保护；
- legacy兼容必须有明确测试，并在代码和实施报告中标记为02-E移除目标。

## 10. 资产API

在不破坏02-C五个任务端点主要HTTP语义的前提下，至少提供：

1. 上传并注册资产；
2. 查询单个资产元数据；
3. 稳定分页列出资产，可按`kind`和`state`过滤；
4. `GET /api/assets/{asset_id}/content`受控读取内容；
5. 软删除/禁用资产；
6. 如实现物理清理，只能是内部Service，不得增加公开“强制删除”旁路。

统一要求：

- UUID不存在、已禁用、已删除、记录存在但文件缺失必须有稳定语义；
- 下载不得接受路径参数；
- 下载应返回正确媒体类型、文件名处理和长度；
- 是否实现HTTP Range应依据现有框架能力；若未实现，不得伪称支持；
- 列表排序必须稳定，并使用稳定游标或沿用02-C已验证分页模式；
- 所有未知异常返回固定、脱敏的500 JSON；
- 禁止返回`backend`、`object_key`、绝对路径、Store根和内部堆栈。

## 11. Worker、Executor与输出资产

### 11.1 输入读取

- 新任务必须通过资产Repository/Service取得资产事实；
- Store根据`backend + object_key`提供本地可读对象；
- Provider Adapter只接收经过受控解析的内部路径或流；
- Worker不得把资产UUID直接拼接到旧`managed_asset_root`；
- 在执行前再次验证资产状态与文件存在性；
- 失效、缺失或内容不一致应映射为明确、脱敏的失败类别。

### 11.2 输出登记

每个有效Provider输出必须：

1. 通过既有远端文件名安全校验；
2. 写入Store唯一临时对象并原子发布；
3. 计算实际size、MIME和SHA256；
4. 创建`kind=output`资产；
5. 创建任务输出关系，保持稳定position；
6. 生成现有`output_metadata`兼容投影；
7. 在完成所需登记后才允许任务进入`succeeded`。

对多个输出：

- 每个输出独立登记；
- 不允许两个关系占用相同position；
- 不允许任务成功但输出关系为空；
- 必须明确部分失败策略。02-D默认采用全体有效输出登记成功后任务才成功；如无法完成全部数据库登记，任务不得假装完整成功；
- 补偿不得删除其他租约或其他执行轮次已经合法登记的对象。

### 11.3 租约与事务

- 失去租约的Worker不得发布新的终态资产、覆盖关系或把任务置为成功；
- 数据库CAS和资产登记的顺序必须有测试覆盖；
- 文件系统与数据库无法形成单一事务，必须采用明确状态、唯一键、幂等登记和补偿；
- 进程在“文件发布后、数据库登记前”崩溃形成的文件必须可被对账识别；
- 进程在“数据库登记后、任务成功前”恢复时不得生成重复资产；
- 不得削弱02-B的submission unknown、恢复、租约和终态协调语义。

## 12. 删除、保留与对账

### 12.1 软删除

- 软删除是02-D公开默认语义；
- 被任务引用的资产允许保留历史关系，但不得再用于创建新任务；
- 已禁用/已删除资产内容默认不可通过公开内容端点下载；
- 重复软删除应幂等；
- 删除时间与状态必须一致。

### 12.2 物理清理

- 只能经内部受控Service；
- 任何`media_job_assets`引用存在时必须拒绝；
- 必须重新校验object key和根边界；
- 数据库状态、文件删除和失败恢复必须有明确顺序；
- 不得递归删除宽泛目录；
- 不得以年龄或文件名猜测用户资产。

### 12.3 最小对账

实现可离线调用、默认只报告不修复的对账Service或命令级函数，至少识别：

- 数据库记录为可用但文件缺失；
- Store正式对象存在但无数据库记录；
- 超过安全阈值的临时对象；
- 任务成功但缺少输出关系；
- 输出关系存在但资产状态不可用。

自动修复、定时调度和生产清理不属于02-D。任何修复模式如确需实现，必须显式参数开启并有测试，不得成为默认。

## 13. 旧`/api/files`窄范围安全修复

必须保留路由和合法兼容行为，但修复以下问题：

1. URL解码后的路径规范化；
2. 绝对路径、drive、UNC、反斜杠、`.`/`..`段拒绝；
3. 每个允许根的最终解析边界校验；
4. 符号链接/junction逃逸拒绝；
5. 非普通文件、缺失文件和不可读文件的稳定响应；
6. 未知异常500脱敏；
7. 不向客户端泄露绝对路径或允许根。

禁止：

- 把旧路由改造成新资产API；
- 改变合法旧URL的正常读取用途，除非该行为本身越出允许根；
