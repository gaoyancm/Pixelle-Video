## 3. 管理API合同

保留03-B原有14个`/api/admin`操作并精确增加6个操作，管理Router总数为20：

| 方法与路径 | 主要语义 |
|---|---|
| `PATCH /batches/{batch_id}/priority` | 更新submitted未归档批次默认优先级，并同步无override且queued无lease的current job |
| `PATCH /items/{item_id}/priority` | 设置、替换或以`null`清除单项override，并在合格时同步current job |
| `GET /batches/{batch_id}/progress` | 按每项最大attempt实时聚合八个互斥桶和derived result |
| `GET /batches/{batch_id}/results` | 稳定返回逻辑项、current attempt、历史attempt、安全job及受管输出投影 |
| `POST /batches/{batch_id}/cancel` | 以operation事实幂等记录current attempt取消请求，不直接写终态或调用远端 |
| `POST /batches/{batch_id}/retry-eligible` | 全批原子创建所有合格current failed job的新attempt |

首次cancel/retry-eligible返回`201`，同键同hash重放返回`200`；同键异hash保持`409 idempotency_conflict`；操作事实矛盾或部分不可解释返回`503 operation_indeterminate`。公开Schema继续隐藏node、Provider、prompt、submission token、对象键、相对/绝对路径和内部异常。

## 4. Worker调度与优先级

Worker每轮先读取并稳定处理`submitting/running`恢复候选，再用剩余容量读取queued候选，保证恢复任务不会被新高优先级任务饿死。恢复候选按`created_at ASC, job_id ASC`；queued候选按`priority DESC, created_at ASC, job_id ASC`。最终领取仍使用阶段02既有status/version/lease CAS，不增加抢占、node slot或全局多Worker并发语义。

批次和单项优先级更新均使用batch version条件更新保护并发；只有current job为queued、`lease_owner`和`lease_expires_at`均为空时才同步调度值，并增加job version。批次响应区分`updated`、`unchanged`、`overridden`和`skipped_claimed_or_nonqueued`；单项响应返回持久化override、effective priority和job是否实际改变。已领取、运行和终态任务保持不变，但偏好继续作为后续管理重试的优先级来源。

## 5. 取消、批量重试与提交未知

取消只处理每项current attempt：非终态未请求时以status/version CAS写`cancel_requested_at`；已请求、终态或缺失事实分别稳定计为`already_requested`、`skipped_terminal`和`not_found`。取消不会调用远端interrupt，不会直接把任务写成cancelled，也不会覆盖真实终态。

retry-eligible在一个短事务内重新核验operation、batch、current attempt、source job、`can_retry`和取消标记。新job ID与幂等键由operation、item和source确定性派生；复制source执行输入、node绑定和input asset relations，priority取当前`coalesce(item override, batch default)`。全部parent job先flush，再写输入关系和`attempt_no=max+1`、`retry_of_attempt_no`；source job、旧attempt、错误、输入和输出事实均保留。零个eligible是会被记录和重放的合法no-op。

cancel和retry-eligible均以`management_operations`为唯一幂等事实源。commit返回未知时检查operation结果及对应取消事实，或job/attempt完整事实：完整匹配返回既有成功；不存在只安全重试一次；缺失或矛盾事实返回`operation_indeterminate`。事务内没有HTTP、Provider、ComfyUI、文件IO或sleep。

## 6. 真实进度与安全结果

Progress只取每项最大attempt关联的current job，分母保持逻辑项数量。每项依固定优先级恰好进入一个桶：先终态`succeeded/failed/timed_out/cancelled`，再非终态`cancel_requested`，最后`queued/submitting/running`。`completed_items`仅计终态；`derived_result`只在全部完成时按`all_succeeded`、`partially_succeeded`、`all_failed`或`completed_with_cancellation`矩阵产生。重试后current attempt回到queued时completed允许下降，不伪造GPU生成百分比，也不写持久化聚合。

Results按`position ASC, item ID ASC`和`attempt_no ASC`返回稳定历史，包含workflow、raw status、取消标志、重试资格、retry血缘、effective priority、时间和安全错误。输出仅来自`media_assets`与output relation，公开文件名、媒体/MIME/大小和安全width/height/duration，并由服务端构造`/api/assets/{asset_id}/content`的`content_href/preview_href`。测试证明响应不含对象键、路径、节点、Provider或prompt；批次归档后历史仍可读取。
