### 21.3 节点绑定责任判定

| 层 | 现状与证据 | 是否应负责本次绑定 |
| --- | --- | --- |
| 公开请求层 | 合同刻意隐藏并禁止`node_id` | 否；不能让客户端选择物理节点 |
| 工作流注册表 | 只定义工作流文件、输入要求和参数目标，不含部署拓扑 | 否 |
| 隔离配置 | `comfyui.nodes[0].id=a800`，enabled且声明本工作流 | 提供路由事实，配置本身正确 |
| 应用服务/生产装配 | 创建内部合同但未注入节点解析结果 | 是；当前缺失点 |
| Repository插入 | 精确保存`create.node_id` | 否；没有把非空值错误改为NULL |
| Worker领取 | 只做lease竞争，不改变不可变请求字段 | 否 |
| Executor | 以持久化节点约束实际Adapter选择，防止恢复时漂移 | 校验责任正确，不应静默接受NULL |

`node_id`被列入`contracts.py::_HASHED_REQUEST_FIELDS`，是幂等请求哈希覆盖的不可变
路由字段；`create_retry_job`也复制父任务的`node_id`。这两项证据排除了“Worker
领取后再修改NULL为a800”作为首选修复：领取后改变该字段会使持久化不可变字段与
创建时`request_hash`不再一致，并改变retry继承语义。

因此节点必须在Repository计算请求哈希和插入任务之前确定。当前没有独立调度器，
最小责任点是生产装配向`MediaJobApplicationService`注入一个只读、确定性的节点
解析器，由应用服务在构造`MediaJobCreate`时设置`node_id`。解析规则必须与
`ComfyUIAdapter.select_node`一致：选择第一个enabled且声明该workflow_type的
配置节点；无匹配节点时在插入前安全失败，不能创建NULL绑定任务。

### 21.5 同时暴露的失败落库缺陷

`RecoverableComfyUIExecutor._submit_new`捕获节点校验异常后调用
`_finish(..., JobStatus.FAILED, ...)`。但任务此时仍为`queued`，而
`state_machine.py::LEGAL_TRANSITIONS`不允许`queued -> failed`。
`transition_owned`在发起数据库CAS之前调用`validate_transition`，所以再次抛出
`InvalidStateTransition`，Worker进程退出，错误和终态均未持久化，lease保留。

这是节点绑定主缺陷触发后的第二个生产失败处理缺口。它不是本次`node_id=NULL`
的成因，但若不补正，任何提交前的参数/配置验证失败仍可能使Worker异常退出。
