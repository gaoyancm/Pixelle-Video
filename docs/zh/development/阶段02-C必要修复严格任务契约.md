## 3. F-01：I2V公开资产字段修复

### 3.1 唯一批准的外部契约

对两个I2V工作流：

- `gpu_4090_wan21_i2v_33f`
- `gpu_4090_wan21_i2v_81f`

外部创建请求必须且只能接受：

`asset_id: string`

要求：

- `asset_id`为单值字符串，不是数组；
- 必须满足既有受管资产ID的安全字符和长度限制；
- 不得为空或只含空白；
- I2V缺少`asset_id`时返回固定422校验错误；
- 外部提交`asset_ids`必须因未知字段被拒绝；
- 外部不得同时提交`asset_id`与`asset_ids`；
- T2V工作流不得接受`asset_id`；
- 客户端仍不得提交任意文件路径、URL或`input_image`。

### 3.2 内部转换

允许服务层或明确的Schema转换层把：

`asset_id`

转换为现有内部表示：

`asset_ids=[asset_id]`

要求：

- 不为修复外部字段而改造02-A/02-B内部任务模型；
- 不改变Repository、Worker或执行器对既有资产列表的语义；
- 不把`asset_ids`重新暴露为公开创建字段；
- 幂等请求摘要必须继续包含规范化后的实际资产语义；
- 同一`asset_id`必须产生稳定、确定的幂等语义；
- 公开文档、OpenAPI、Schema和测试必须统一使用`asset_id`。

### 3.3 响应边界

本修复不授权新增资产详情、下载地址、文件路径或资产管理端点。除非原批准响应已经明确包含安全资产字段，否则不得借此扩大响应。

## 4. F-02：公开参数强校验

### 4.1 基本原则

不得继续使用仅检查键名的`dict[str, Any]`作为最终公开校验。

对每个允许公开的参数，必须定义：

- 明确数据类型；
- 必要的最小值和最大值；
- 必要的枚举集合；
- 字符串最小/最大长度；
- 是否必填及默认值语义；
- 适用于哪些工作流。

所有校验必须在持久化任务创建前完成。无效请求不得创建任务、幂等记录或其他数据库副作用。

### 4.2 唯一来源与防漂移

工作流名称白名单必须继续以：

`pixelle_video/services/comfyui_workflows.py::WORKFLOW_SPECS`

为唯一来源，不得复制第二份工作流名称白名单。

参数规则应优先：

1. 复用既有注册信息中的约束；
2. 或从该注册信息派生；
3. 若既有注册信息没有足够约束，可增加与该注册表相邻、集中且可测试的公开参数元数据；
4. 不得把规则分别散落在Router、Service、测试和文档中形成多套真相来源。

如果真实仓库无法在不修改本契约禁止范围的前提下建立可靠的唯一约束来源，必须停止并报告，不得自行扩大改造。

### 4.3 最低拒绝要求

至少必须拒绝：

- 数字字段使用字符串、对象、数组或布尔值冒充；
- 字符串字段使用对象或数组；
- `prompt`为空、仅空白、类型错误或超过批准长度；
- `negative_prompt`类型错误或超过批准长度；
- `width`、`height`、`steps`、`cfg`、`seed`等字段的错误类型；
- 数值低于最小值或高于最大值；
- 负数`steps`；
- 非有限浮点值；
- 未批准枚举值；
- 当前工作流不适用的参数；
- 未知参数；
- 参数数量或序列化体积超过既有限制。

独立验收中已经确认会被错误接受的以下值必须被稳定拒绝：

- `width="not-an-integer"`
- `prompt={"nested":"object"}`
- `steps=-999`
- `cfg="bad"`

### 4.4 约束值的确定

实施Codex必须先根据真实工作流注册信息、现有执行器参数和已验证工作流文档，整理一张“公开参数—类型—范围—适用工作流—来源”表，再实施校验。

不得凭空发明与真实工作流不兼容的范围。若某个参数的可靠上下限无法由仓库证据确定：

- 允许采用能够排除明显非法值的保守安全约束；
- 必须在修复报告中写明证据、选择和限制；
- 若该选择会实质限制已有合法调用，必须停止并申请决策。

不得修改4个工作流JSON来适配API校验。

### 4.5 错误语义

参数类型、范围、枚举、长度和适用性错误统一使用原契约批准的固定422校验结构：

```json
{
  "error": {
    "code": "invalid_request",
    "message": "The request is invalid."
  }
}
```
可以保留安全、结构化的字段定位信息，但不得返回内部Schema类名、Python异常、文件路径、工作流节点内部信息或原始异常文本。

## 5. F-03：未知异常固定响应

### 5.1 必须行为

5个`/api/media/jobs`端点发生未分类异常时，必须返回：

- HTTP `500`；
- `Content-Type: application/json`；
- 固定、脱敏结构；
- 不包含原始异常消息、异常类名、堆栈、路径、DSN、Token、幂等键或下游响应。

批准的最低响应为：

```json
{
  "error": {
    "code": "internal_error",
    "message": "An internal error occurred."
  }
}
```

### 5.2 实现边界

- 不得用宽泛异常捕获吞掉已知业务错误；
- 已知404、409、422、503映射必须保持不变；
- 未知异常应保留服务端可诊断日志，但日志不得记录秘密、原始幂等键或完整敏感请求；
- 不得把原始异常字符串拼入客户端响应；
- 异常处理应只影响本阶段新API，不得无授权改变旧API的全局错误行为；
- 如必须增加全局处理器，必须证明旧API响应没有被改变，否则停止报告。

## 6. F-04：必须补齐的测试

### 6.1 F-01资产字段

必须测试：

- 两个I2V工作流分别接受单值`asset_id`；
- I2V缺少`asset_id`被拒绝；
- `asset_ids`被拒绝；
- T2V提交`asset_id`被拒绝；
- 非法字符、空值和超长`asset_id`被拒绝；
- 外部单值正确转换为内部单元素列表；
- OpenAPI只显示`asset_id`，不显示公开`asset_ids`；
- 幂等同语义仍稳定命中。

### 6.2 参数边界

每类公开参数至少覆盖：

- 一个合法值；
- 错误类型；
- 最小值边界；
- 最大值边界；
- 低于最小值；
- 高于最大值；
- 不适用工作流；
- 未知字段；
- 超长字符串；
- 验收报告列出的4个非法样例。

测试必须确认无效请求不会创建任务或幂等记录。

### 6.3 分页

必须通过真实API和持久化Repository组合验证：

- `limit + 1`行不会泄露到当前页；
- 连续至少两页无重复；
- 连续至少两页无漏项；
- 同`created_at`时`job_id DESC`稳定；
- 状态过滤与分页组合正确；
- `has_more`在中间页和末页正确；
- 响应不包含`total`。

### 6.4 重试幂等与并发

必须补充API级测试：

- 对同一原任务并发提交相同重试键只产生一个新任务；
- 同一原任务的幂等命中返回同一新任务；
- 不同原任务使用相同原始键不会错误复用；
- 创建与重试使用相同原始键相互隔离；
- 原任务在上述操作后保持不变；
- 新任务血缘正确。

### 6.5 异常与可用性

必须使用响应级测试，且在需要时采用`raise_app_exceptions=False`，验证：

- 未知异常返回固定脱敏500 JSON；
- 原始异常文本不出现在响应；
- `service_unavailable`返回固定503 JSON；
- 已知业务错误不会被错误转换为500；
- OpenAPI响应Schema不暴露禁止字段；
- 正常与错误响应都不泄露路径、DSN、Token、租约、内部版本或堆栈。

### 6.6 架构边界

不得只依赖源码字符串扫描。应采用不启动外部服务的导入、依赖或行为测试，证明：

- 新Router导入不启动Worker、迁移、建表、Uvicorn或外部连接；
- Router不直接依赖旧`TaskManager`、ComfyUI执行器或ORM业务流程；
- API请求不会直接调用ComfyUI；
- 旧入口注册仍存在且未被改写；
- 测试不得通过过度Mock绕过真正需要验证的Schema、事务和Repository行为。

如需要保留原字符串扫描，可以作为补充，但不能作为唯一证据。
