## 6. 幂等、并发与事务

- `Idempotency-Key`格式严格限制为1至128个安全ASCII字符。
- 原始键经`operation + source_job_id + raw_key`的SHA-256作用域化，原始键不直接持久化。
- 创建与重试作用域隔离，不同重试来源隔离。
- Repository在短事务中插入，数据库唯一约束处理并发竞争；`IntegrityError`后按作用域键读取既有行并核对请求语义。
- 创建请求哈希覆盖工作流、工作流键、executor、provider、node、参数、资产及deadline等不可变语义，并使用确定性JSON规范化。
- 并发创建测试8路只产生一个任务；并发重试Repository测试8路只产生一个子任务。
- 重试在同一短事务内读取原任务、调用`can_retry()`并插入子任务；原任务不修改。
- SQLite并发结果不能外推为PostgreSQL多节点生产保证；实施报告对此有明确限制。

## 7. 查询、分页、取消与重试

### 7.1 查询与分页

- 不存在任务映射为`404 job_not_found`。
- `limit`为1至100，`offset`非负，状态使用`JobStatus`枚举。
- Repository固定按`created_at DESC, job_id DESC`排序。
- 应用服务读取`limit + 1`并计算`has_more`，不计算或返回`total`。
- 同时间戳次排序有Repository测试；现有API测试验证`has_more`和过滤，但未完整验证跨页无重复/无漏项，见F-04。

### 7.2 取消

- 只通过CAS写入`cancel_requested_at`，不改变状态，不调用远程GPU取消或ComfyUI全局`/interrupt`。
- 重复取消直接返回已有请求标记，语义幂等。
- 终态拒绝为`409 job_not_cancelable`。
- 文档未承诺远程计算立即停止；完整回归覆盖既有Worker安全点和终态协调。

### 7.3 重试与血缘

- 严格复用状态机`can_retry()`；`submission_unknown`不可重试。
- 新任务有新`job_id`、新submission token、递增`retry_count`和服务端设置的`retry_of_job_id`。
- 原失败任务保持不变；创建与重试幂等作用域及不同来源作用域隔离。
- 并发同键由唯一约束归一为一个子任务。

## 11. 问题清单

### F-01 — P1 必须修复：I2V公开资产字段与批准契约不一致

- 位置：`api/schemas/media_jobs.py:25,34-40,53-56`；`docs/zh/development/persistent-media-jobs-phase2c-api.md:23`
- 证据：批准的公开说明要求单个受管`asset_id`；真实Schema只接受复数`asset_ids: list[str]`，I2V再约束列表长度为1。请求`asset_id`会因额外字段被拒绝。
- 影响：这不是内部表示差异，而是外部JSON字段名和形状不同；按公开契约构造的I2V客户端无法创建任务。
- 建议修复方向：由下一轮授权决定唯一公开字段；若批准契约保持`asset_id`，外部Schema应使用单值字段，内部再转换为资产列表。同步代码、OpenAPI、文档和测试。

### F-02 — P1 必须修复：`parameters`只限制键名，不校验值类型和范围

- 位置：`api/schemas/media_jobs.py:24,42-57`
- 证据：`parameters`声明为`dict[str, Any]`；校验只检查数量、允许键名和序列化字节数。独立只读复现中，下列非法值均成功通过`MediaJobRequest.model_validate()`：
  - T2V：`width="not-an-integer"`、`prompt={"nested":"object"}`
  - I2V：`steps=-999`、`cfg="bad"`
- 影响：API接受明显不符合工作流节点语义的请求并持久化为queued任务，把可在入口稳定拒绝的错误延迟到Worker/ComfyUI；违反“受控parameters”和“非法参数稳定拒绝”的核心契约，也会让相同幂等键绑定无效任务。
- 建议修复方向：为公开参数定义按工作流适用的强类型、范围、枚举及字符串长度规则；从唯一注册信息或批准的共享约束派生，不另建漂移白名单；增加每类非法类型/边界测试。

### F-03 — P2 应修复：未知异常不满足统一JSON错误结构

- 位置：`api/routers/media_jobs.py:37-61`
- 证据：Route只捕获`RequestValidationError`、已知业务异常、`IdempotencyConflictError`、`MediaJobsDisabledError`和`SQLAlchemyError`，无未知异常兜底；FastAPI/Starlette默认500不保证任务规定的`{"error":{"code":"...","message":"..."}}`结构。
- 影响：未分类运行时错误会破坏新API固定错误契约；现有测试没有覆盖该分支。默认生产500通常不包含堆栈，但结构仍不符合批准契约。
- 建议修复方向：在不泄露异常文本的前提下增加固定、脱敏的500映射，并保留服务端日志/追踪；增加`raise_app_exceptions=False`的响应级测试。

### F-04 — P2 应修复：关键测试覆盖仍有缺口

- 位置：`tests/test_media_jobs_api.py:128-166,199-270`
- 证据：
  - API分页只验证第一页`has_more`，没有跨页组合验证无重复、无漏项及不暴露第`limit+1`行。
  - 未测试不同原任务使用相同原始重试键的API级隔离，也未对API端点发起并发重试。
  - 未测试未知异常的固定错误结构、`service_unavailable`分支或OpenAPI响应Schema脱敏。
  - 参数拒绝用例只有未知键/内部字段，没有非法类型和范围，因此未发现F-02。
  - 架构边界测试是源码字符串禁用词检查，不能证明间接导入、启动副作用或依赖方向。
- 影响：测试数量达到31个净新增，但对若干任务文件明确要求的边界证据不足；全绿不能证明这些契约成立。
